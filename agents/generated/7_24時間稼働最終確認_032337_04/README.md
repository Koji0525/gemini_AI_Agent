# 24時間稼働自律システム 最終確認モニター

## 概要

このプロジェクトは、24時間自律稼働システムが本番運用に耐えうる状態であることを最終確認するための監視ツールです。
システムが長時間無人で稼働しても問題が発生しないことを保証することを目的としています。
本ツールは、システムのリソース使用状況、API利用状況、ログに記録されたエラーや自己修復・自己進化イベントを監視し、その結果をレポートとして出力します。
これにより、システム運用における潜在的な問題を早期に特定し、安定稼働への最終的な確証を得ることができます。

## 目的

*   **システム安定性の保証**: 24時間連続稼働中にメモリリーク、CPU高負荷、ディスク容量不足などのリソース問題が発生しないことを確認します。
*   **エラーハンドリングの有効性検証**: システムに組み込まれた自己修復（F7）機能や人間通知（F9）機能、リトライ機構が正常に動作し、エラー発生時に適切に対応できることを確認します。
*   **学習サイクルの健全性確認**: 自己進化（F8）トリガーやナレッジ蓄積が期待通りに動作し、システムが継続的に学習・改善していることを確認します。
*   **API利用状況の監視**: Claude API、Google Sheets APIなどの外部APIの使用量が許容範囲内に収まり、レート制限に抵触しないことを確認します。
*   **ログ管理の適切性確認**: ログローテーションが適切に行われ、重要イベントが正確に記録・通知されていることを確認します。
*   **本番運用準備**: 上記の確認項目をクリアすることで、システムが本番環境で安心して運用できる状態であることを保証します。

## 機能

本監視ツールは以下の主要な機能を提供します。

1.  **長時間稼働テストの補助**:
    *   **リソース監視**: CPU使用率、メモリ使用量、ディスク使用量を定期的に（デフォルト60秒間隔）収集し、閾値を超過した場合は警告を発します。
    *   **データ記録**: 監視されたリソースデータはCSVファイルに保存され、後で詳細な分析が可能です。
2.  **エラーハンドリング検証の補助**:
    *   **ログ解析**: 監視対象システムのログディレクトリを定期的にスキャンし、「F7 Failed」、「F9 Triggered」、「Error」、「Exception」、「Retry limit exceeded」などのエラー関連パターンを検出します。
    *   **通知**: 重要なエラーイベントが検出された場合、コンソールに警告をログ出力し、将来的な通知システム（Slack, Emailなど）との連携を可能にします。
3.  **学習サイクル動作確認の補助**:
    *   **ログ解析**: 「F8 Triggered」、「Knowledge Updated」、「Pattern Learned」などの学習サイクル関連パターンをログから検出し、システムが自己進化していることを確認します。
    *   **通知**: 学習イベントが検出された場合もログ出力により通知します。
4.  **API使用量の監視**:
    *   **シミュレーションと記録**: 設定ファイルに基づき、API呼び出しをシミュレートし、日次呼び出し制限や1秒あたりのリクエスト数（RPS）制限に近づいているか監視します。
    *   **警告**: API使用量が閾値（例: 制限の80%）を超えた場合に警告を発します。
5.  **ログ管理の確認**:
    *   **ログファイル存在・更新チェック**: 監視対象のログファイルが定期的に更新されているかを確認します。
    *   **ローテーション確認**: ログディレクトリ内のファイル名や更新日時から、ログローテーションが適切に実施されているか確認する手助けをします。
6.  **最終レポート生成**:
    *   監視期間終了後、収集したデータに基づき、リソース使用状況のサマリー、API利用統計、検出されたイベントの概要を含むレポートを自動生成します。
    *   レポートには、最終確認の成功基準に対する達成状況も記載されます。

## インストール

本ツールを実行するにはPython 3.6以上と以下のライブラリが必要です。

1.  **psutil**: システムリソース監視に使用します。
2.  **PyYAML**: 設定ファイル（`config.yaml`）の読み込みに使用します。

インストール手順:

1.  **Pythonのインストール**:
    お使いのOSにPython 3.6以上がインストールされていることを確認してください。
    インストールされていない場合は、公式ウェブサイト (https://www.python.org/downloads/) からダウンロードしてインストールしてください。

2.  **必要なライブラリのインストール**:
    以下のコマンドを実行して、必要なライブラリをインストールします。
    ```bash
    pip install psutil PyYAML
    ```

3.  **プロジェクトのクローンまたはダウンロード**:
    このリポジトリをクローンするか、ファイルをダウンロードして任意のディレクトリに配置してください。

## 使用方法

### 1. 設定ファイルの準備 (`config.yaml`)

`config.yaml`ファイルは、監視ツールの動作をカスタマイズするための設定を含んでいます。
もしこのファイルが存在しない場合、`main.py`の初回実行時にデフォルト設定が生成されます。
生成されたファイルをベースに、環境に合わせて内容を調整してください。

```yaml
# config.yamlの例
monitoring:
  interval_seconds: 60       # 監視間隔（秒）。デフォルトは60秒。
  duration_hours: 6          # 監視の合計時間（時間）。本番運用前の最終確認では最低6時間以上推奨。
  resource_thresholds:
    cpu_percent_high: 80     # CPU使用率の警告閾値（パーセント）
    memory_percent_high: 90  # メモリ使用率の警告閾値（パーセント）
    disk_percent_high: 95    # ディスク使用率の警告閾値（パーセント）
  log_directory: "logs/"     # 監視対象システムのログファイルが保存されているディレクトリ
  output_data_directory: "monitor_data/" # 監視結果データやレポートの出力先ディレクトリ

api_monitoring:
  claude_api:                 # Claude APIの監視設定
    max_daily_calls: 100000   # 1日の最大呼び出し回数
    max_rps: 5                # 1秒あたりの最大リクエスト数
  google_sheets_api:          # Google Sheets APIの監視設定
    max_daily_calls: 50000
    max_rps: 10

log_analysis:
  error_patterns:             # ログから検出するエラー関連のパターン
    - "ERROR"
    - "Exception"
    - "F7 Failed"             # 自己修復失敗を意味するログパターン
    - "F9 Triggered"          # 人間通知トリガーを意味するログパターン
    - "Retry limit exceeded"  # リトライ制限超過を意味するログパターン
  learning_patterns:          # ログから検出する学習関連のパターン
    - "F8 Triggered"          # 自己進化トリガーを意味するログパターン
    - "Knowledge Updated"     # ナレッジ蓄積を意味するログパターン
    - "Pattern Learned"       # パターン学習を意味するログパターン

notifications:
  enabled: True               # 通知を有効にするか（現在の実装ではログ出力のみ）
```

**重要**: `log_directory`は、`sh/run_autonomous_24h_v3.sh`スクリプトがログを出力する先のパスと一致させてください。

### 2. 監視の実行

ターミナルまたはコマンドプロンプトを開き、プロジェクトのルートディレクトリに移動して以下のコマンドを実行します。

```bash
python main.py
```

監視が開始され、設定された`duration_hours`の時間だけ実行されます。
実行中は、コンソールに監視状況が出力され、`system_monitor.log`ファイルに本ツール自身のログが記録されます。

### 3. 結果の確認

監視が完了すると、`output_data_directory`（デフォルトは`monitor_data/`）に以下のファイルが出力されます。

*   `monitoring_report_YYYYMMDD_HHMMSS.txt`: 監視期間全体のサマリーレポート。
*   `resource_monitoring_data_YYYYMMDD_HHMMSS.csv`: 詳細なリソース使用率データ。
*   `detected_log_events.json`: ログから検出された全てのエラーや学習イベントの詳細。

これらのファイルをレビューし、システムが期待通りに動作したかを確認してください。

## 成功基準

この監視ツールの「成功」は、以下の基準を達成することで判断されます。

*   **6時間以上の連続稼働が成功する**: `monitoring_report_YYYYMMDD_HHMMSS.txt`で報告される稼働時間が設定した期間を満たしていること。そして、その期間中にCRITICALレベルのリソース警告が頻発していないこと。
*   **エラー時の自動修復(F7)が正常に動作する**: `detected_log_events.json`またはレポートで「F7 Failed」が検出されていないこと。また、リトライ回数に関する異常なログが見られないこと。
*   **学習サイクル(F8)が自動実行される**: `detected_log_events.json`またはレポートで「F8 Triggered」や「Knowledge Updated」などの学習イベントが定期的に検出されていること。
*   **API使用量が許容範囲内に収まる**: `monitoring_report_YYYYMMDD_HHMMSS.txt`のAPIサマリーで、日次呼び出し数やRPSが設定された最大値を大幅に下回っていること。CRITICALレベルのAPI使用量警告がログにないこと。
*   **詳細なチェックリストが作成される**: 本README.mdに記載されたチェックリスト項目と、本ツールが生成するレポートが、本番運用前の最終確認に必要な情報を提供できていること。

### 起動前チェック項目

*   [ ] `config.yaml`の設定が本番環境と監視目的に合わせて適切に設定されているか。
    *   `log_directory`が監視対象システムのログパスを正確に指しているか。
    *   リソース閾値がシステムの許容範囲内に設定されているか。
    *   API制限値が最新の仕様と一致しているか。
*   [ ] 監視対象システム（`sh/run_autonomous_24h_v3.sh`）が事前に正常に起動し、ログ出力が開始されているか。
*   [ ] 必要なPythonライブラリ（`psutil`, `PyYAML`）がインストールされているか。
*   [ ] 出力ディレクトリ（`monitor_data/`）への書き込み権限があるか。
*   [ ] 既存のログファイルや監視データが、今回のテストに影響を与えないよう整理されているか。

### 稼働中監視項目

*   [ ] 監視ツール自身がエラーなく正常に動作しているか（`system_monitor.log`を確認）。
*   [ ] コンソール出力または`system_monitor.log`にCRITICAL/ERRORレベルの警告が頻繁に出ていないか。
*   [ ] 監視対象システムのログ（`logs/`ディレクトリ内）が活発に更新されているか。
*   [ ] 特定のリソース（CPU, メモリ, ディスク）が長時間にわたって閾値近くで推移していないか。
*   [ ] API使用量に関するWARNING/CRITICAL通知が頻繁に発生していないか。
*   [ ] 「F7 Failed」や「F9 Triggered」のイベントが検出されていないか、または適切に処理されているか。
*   [ ] 「F8 Triggered」や「Knowledge Updated」などの学習イベントが適時検出されているか。

### 停止時確認項目

*   [ ] 監視ツールが設定された`duration_hours`を完遂し、正常に終了したか。
*   [ ] `monitor_data/`ディレクトリに最終レポート（`.txt`）、詳細データ（`.csv`）、イベントログ（`.json`）が全て出力されているか。
*   [ ] 生成されたレポートを詳細に確認し、以下の点を分析する。
    *   リソース使用率の最大値と平均値が許容範囲内であるか。
    *   APIの推定日次呼び出し数と平均RPSが制限を大きく下回っているか。
    *   検出されたエラーイベントがゼロ、または許容範囲内であるか。
    *   学習サイクルイベントが期待通りに発生しているか。
*   [ ] `detected_log_events.json`内の詳細なイベントログを確認し、システム異常がないことを確認する。
*   [ ] ログローテーションが実際に機能している痕跡（古い日付のログファイルなど）が`logs/`ディレクトリに存在するか。
*   [ ] 全ての成功基準が満たされたことを確認し、システムの本番運用準備が完了したと判断する。

## API仕様（このツールの設定可能な項目について）

この監視ツールは外部APIを提供しませんが、`config.yaml`を通じてその動作を細かく設定できます。
主要な設定項目とそれらがシステムの動作に与える影響を以下に示します。

*   **`monitoring.interval_seconds`**: 監視ループが各チェックを実行する間隔を秒単位で指定します。値を小さくすると詳細なデータを取得できますが、システムへの負荷が増加します。
*   **`monitoring.duration_hours`**: 監視ツールが実行され続ける時間を時間単位で指定します。タスク要件の「最低6時間連続」を満たすように設定してください。
*   **`monitoring.resource_thresholds`**: CPU, メモリ, ディスクの使用率に関する警告閾値をパーセントで指定します。これらの閾値を超えると通知がトリガーされます。
*   **`monitoring.log_directory`**: 監視対象のシステムログが存在するディレクトリのパスを指定します。`utils.py`の`parse_log_file_for_patterns`関数がこのディレクトリ内のログファイルを読み込みます。
*   **`api_monitoring.<api_name>.max_daily_calls`**: 特定のAPIに対する1日あたりの最大呼び出し回数を指定します。本ツールはこれを基準に警告を発します。
*   **`api_monitoring.<api_name>.max_rps`**: 特定のAPIに対する1秒あたりの最大リクエスト数を指定します。本ツールはこれを基準に警告を発します。
*   **`log_analysis.error_patterns`**: ログファイル内でエラーと判断する文字列パターンのリスト。これらのパターンが見つかるとエラーイベントとして記録されます。
*   **`log_analysis.learning_patterns`**: ログファイル内で学習サイクルに関連するイベントと判断する文字列パターンのリスト。これらのパターンが見つかると学習イベントとして記録されます。
*   **`notifications.enabled`**: 通知機能の有効/無効を切り替えます。現在、通知はログ出力として実装されていますが、将来的に外部サービスと連携するためのフックとなります。

これらの設定項目を適切に調整することで、システムの特性に合わせた柔軟な監視が可能です。
