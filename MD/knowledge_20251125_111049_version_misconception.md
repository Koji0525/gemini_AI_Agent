# 🚨 重大な発見: v51は「未使用」だった

## 🎯 問題の本質

### 誤認識の経緯
```
当初の判断:
「v51が最新版」と思い込んだ

根拠:
- ファイル名のバージョン番号（v51 > v31）
- ファイルの更新日時

実際の調査結果:
「integrated_orchestrator.py（正規版）が本流」

証拠:
- 参照数: 15件（プロジェクト全体で最多）
- サイズ: 26K, 677行（v51の3倍）
- 使用箇所: 主要スクリプト、テストで使用
```

## 🔍 根本原因分析（15層）

### なぜ1: なぜv51が最新と思ったか？
**答え**: ファイル名のバージョン番号（v51 > v31）

### なぜ2: なぜバージョン番号を信じたか？
**答え**: セマンティックバージョニングの常識

### なぜ3: なぜ実際の使用状況を確認しなかったか？
**答え**: ファイルリストだけで判断した

### なぜ4: なぜファイルリストだけで判断したか？
**答え**: `ls -lt` でソートして最新を特定する方法に慣れていた

### なぜ5: なぜこの方法が通用しなかったか？
**答え**: このプロジェクトでは**バージョン番号とファイル名が一致しない**

### なぜ6: なぜバージョン番号とファイル名が一致しないか？
**答え**: 複数の開発ラインが並行して進んでいた

**証拠**:
- v45系: v45_1, v45_2, v45_3（派生）
- v31系: v31_master, v31_core（用途別）
- 正規版: バージョン番号なし

### なぜ7: なぜ複数の開発ラインが並行したか？
**答え**: 実験的機能の試作と本流の並行開発

### なぜ8: なぜ本流にバージョン番号がないか？
**答え**: 正規版として常に最新を保つため

### なぜ9: なぜこのルールを知らなかったか？
**答え**: ドキュメント化されていなかった

### なぜ10: なぜドキュメント化されていなかったか？
**答え**: 暗黙知として共有されていた

### なぜ11: なぜ暗黙知に依存していたか？
**答え**: 開発初期は少人数だった

### なぜ12: なぜAI開発で問題化したか？
**答え**: AIは暗黙知にアクセスできない

### なぜ13: なぜAIにとって暗黙知が問題か？
**答え**: ファイル内容ではなくメタ情報（使用頻度）に依存

### なぜ14: なぜメタ情報を取得しなかったか？
**答え**: 静的分析（ファイル一覧）で済ませた

### なぜ15: なぜ動的分析（参照検索）が必要だったか？
**答え**: このプロジェクトの命名規則が非標準だったから

## 🎯 真因
```
「バージョン番号付きファイルは実験用、
正規版（バージョン番号なし）が本流」

というプロジェクト固有のルールが
明文化されておらず、AIが誤認識した
```

## ✅ 正しい判断方法

### 最新版の特定手順
```bash
# ❌ 間違った方法
ls -lt scripts/integrated_orchestrator*.py | head -1
# → v51を返すが、これは未使用

# ✅ 正しい方法
# 1. 全ファイルを取得
find scripts/ -name "integrated_orchestrator*.py"

# 2. 各ファイルの参照数を調査
grep -r "integrated_orchestrator" --include="*.py" . | \
    grep -v "\.pyc\|__pycache__" | \
    cut -d: -f1 | sort | uniq -c | sort -rn

# 3. 最も多く参照されているファイル = 最新版
```
