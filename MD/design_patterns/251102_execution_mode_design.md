# 実行モード制御の設計パターン（v1.0）

## 🔍 なぜなぜ分析：テストモード待機問題

### 発生した問題
テストモードで`TEST_MODE=true`を設定しても、1時間待機が発生する

### なぜなぜ分析（10層）

1. **なぜ待機が発生する？**
   → `else`節が実行されている

2. **なぜelse節が実行される？**
   → `if self.test_mode:`が期待通り動作していない

3. **なぜ期待通り動作しない？**
   → 別の場所（IntegratedOrchestrator）でも待機している

4. **なぜ別の場所で待機？**
   → 二重ループ構造（外側：Autonomous24HSystem、内側：IntegratedOrchestrator）

5. **なぜ二重ループ構造？**
   → 既存のOrchestratorをラップして新機能を追加した

6. **なぜラップした？**
   → 既存コードを変更せず、影響範囲を小さくしたかった

7. **なぜ影響範囲を小さく？**
   → 既存機能を壊さないため

8. **なぜ既存機能を壊す懸念？**
   → 統合されたテストがなく、動作保証ができない

9. **なぜ統合テストがない？**
   → 急速な開発で、テストインフラが整備されていない

10. **根本原因**
    → **設計思想の不在**：拡張性と制御の統一が考慮されていない

---

## 🎯 抜本的解決策：実行制御の統一設計

### 設計原則

1. **Single Source of Truth（単一の真実の源）**
   - 実行モード設定は1箇所で管理
   - 全コンポーネントが同じモードを参照

2. **Explicit is Better than Implicit（明示的 > 暗黙的）**
   - モード切替は明示的なパラメータで
   - 環境変数に依存しない設計も可能に

3. **Separation of Concerns（関心の分離）**
   - 実行制御と業務ロジックを分離
   - Orchestratorは業務ロジックに専念

4. **Reusability（再利用性）**
   - 他のシステムでも使える汎用設計
   - プラグイン可能なアーキテクチャ

---

## 📐 新設計：ExecutionController パターン

### アーキテクチャ
```
┌─────────────────────────────────────┐
│   ExecutionController (統一制御)    │
│  ┌─────────────────────────────┐   │
│  │ ExecutionMode (モード管理)   │   │
│  │ - test_mode                 │   │
│  │ - max_cycles                │   │
│  │ - wait_interval             │   │
│  └─────────────────────────────┘   │
│                                     │
│  ┌─────────────────────────────┐   │
│  │ CycleManager (サイクル制御)  │   │
│  │ - should_continue()         │   │
│  │ - should_wait()             │   │
│  │ - get_wait_time()           │   │
│  └─────────────────────────────┘   │
└─────────────────────────────────────┘
           ↓ 統一インターフェース
┌─────────────────────────────────────┐
│    IntegratedOrchestrator           │
│    (業務ロジックに専念)              │
└─────────────────────────────────────┘
```

### メリット

1. **拡張性**
   - 新しい実行モード追加が容易
   - デバッグモード、ドライランモードなど

2. **テスタビリティ**
   - モックに置き換え可能
   - ユニットテスト容易

3. **再利用性**
   - 他のエージェントでも使用可能
   - 標準パターンとして展開

4. **保守性**
   - 制御ロジックが1箇所に集約
   - バグ修正が容易
